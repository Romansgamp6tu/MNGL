# Как устроено приложение MNGL

Эта страница объясняет порядок работы приложения и связи между объектами. Сначала соберите [первое окно с отрисовкой](../2d/quick-start.md), затем возвращайтесь сюда, когда начнёте добавлять ввод, ресурсы и несколько сцен.

## Какой уровень API выбрать

| Задача | Начальный интерфейс | Когда нужен следующий уровень |
|---|---|---|
| Открыть окно, получить ввод | `window`, `input` | `render_window`, когда понадобится рисование |
| Рисовать спрайты, фигуры и текст | `render_window::frame()`, `sprite`, `text` | `two_d::renderer` для собственного GPU lifecycle |
| Сделать миникарту, экран инвентаря, эффект | `texture::frame()` и вывод текстуры как спрайта | GPU-проходы, если нужен собственный pipeline |
| Обрабатывать управление игроком | `action_map`, `input_context` | Физические устройства для переназначения и нескольких игроков |
| Проиграть эффект или музыку | `audio::load_sound` / `audio::load_music`, `audio::play` | PCM-потоки, capture и собственный backend |
| Прочитать настройки | `paths` и стандартные файловые потоки | `storage` для SDL-хранилищ, `async_io` для фонового I/O |

Подключайте публичные заголовки: `<MNGL/render_window.hpp>`, `<MNGL/action_map.hpp>` и т. п. `mngl.hpp` удобен как общий заголовок, но включает в том числе аудио. Файлы `MNGL/detail/` — реализация; путь к ним может измениться между версиями.

## Один кадр: события, логика, рисование

| Порядок | Действие | Что уже можно использовать |
|---|---|---|
| До цикла | Создать окно, загрузить изображения и шрифты, настроить действия | Ресурсы живут между кадрами |
| 1 | Вызвать `input::next_frame()` один раз | События обработаны, состояния ввода и `delta_time()` обновлены |
| 2 | Прочитать ввод, обновить игру | `pressed()` для нового нажатия, `down()` для удержания |
| 3 | Начать `window.frame(clear_color)` | Активная цель готова принимать draw-команды |
| 4 | Вызвать `frame.draw(...)` | Объекты добавляются в кадр в порядке вызовов |
| 5 | Вызвать `frame.display()` | Кадр завершён, команды отправлены |

`input::next_frame()` также обновляет зарегистрированные `updatable`. Собственную игровую логику можно вызывать обычными функциями. `sprite_animation` обновляется явно через `update(dt)`; повторный вызов и вручную, и из своего `updatable` ускорит её вдвое.

Фрагмент ниже вставляется в цикл из быстрого старта. `player` — заранее созданный спрайт; скорость задаётся в единицах сцены за секунду:

```cpp
#include <algorithm>

const float dt = static_cast<float>(std::min(mngl::input::delta_time(), 0.1));
float direction = 0.0f;
for (const auto& keyboard : mngl::input::keyboards())
{
	if (keyboard.down(mngl::scancode::d)) direction += 1.0f;
	if (keyboard.down(mngl::scancode::a)) direction -= 1.0f;
}
auto position = player.position();
position.x += direction * 0.5f * dt;
player.position(position);
```

Ограничение `dt` — политика этого примера: после долгой остановки в отладчике объект не перескочит всю сцену. Для точной симуляции используйте собственный фиксированный шаг. `input::max_fps()` ограничивает частоту цикла, но не заменяет время в расчёте движения.

`pressed()` и `released()` действуют один кадр. Два запроса `pressed()` в одном кадре возвращают одно состояние: чтение его не «потребляет». Поэтому несколько игровых систем могут увидеть одно нажатие. Для меню и игры выбирайте активный контекст самостоятельно; подробности — в [рецептах управления](../core/input-recipes.md).

## Три системы координат

| Значение | Единицы и начало координат | Для чего |
|---|---|---|
| `window.size()` и позиция мыши SDL | Логические координаты окна, начало сверху слева | Размер окна, события мыши, UI |
| `window.pixel_size()` | Физические пиксели drawable-области | Размер GPU-цели и HiDPI |
| `sprite.destination` и `view` | Координаты сцены, начало по умолчанию снизу слева | Положение игровых объектов |

Без собственного `view` короткая сторона сцены равна `1`. У окна `800 × 600` область имеет размер приблизительно `{1.333, 1}`: спрайт шириной `100` окажется намного больше экрана. Относительные размеры удобно брать через `window.coordinate_size()`.

Пользовательский `view` задаёт видимую область мира; при изменении пропорций цели MNGL расширяет её по одной оси. Поэтому для перевода мыши в мир важна фактически видимая область `view::visible_area()`, а не только исходный прямоугольник камеры. [Руководство по координатам](../2d/coordinates-and-view.md) содержит готовый перевод и пример камеры.

## Кто чем владеет

| Объект | Владение | Практическое правило |
|---|---|---|
| `texture` | Владеет GPU-текстурой; перемещается, не копируется | Переместите обычный ассет в `texture_store` до цикла |
| `texture_handle` | Непрозрачный индекс с идентификатором store | Handle разрешается только через выдавший его store |
| `sprite(store, handle)` | Хранит handle, а не адрес объекта `texture` | Спрайт можно перемещать и копировать вместе с контейнерами |
| `sprite::borrowed(texture)` | Явно заимствует внешний ресурс | Объект текстуры должен оставаться живым и по тому же адресу, пока используется спрайт; для обычных ассетов берите handle из `texture_store` |
| `texture_store` | Владеет добавленными страницами | Store должен жить дольше renderer и кадров, использующих его ресурсы |
| `texture_region` | Handle страницы и UV-границы | Копирование региона не копирует текстуру |
| `sprite_animation` | Владеет списком кадров и состоянием времени | Страницы атласа остаются в texture store |
| `font` и `text` | Текст использует выбранный шрифт | Шрифт должен жить дольше рисуемого текста и использующих его кадров |
| `frame_scope` | Управляет активным кадром, заимствует цель | Окно/целевая текстура живут до `display()` или отмены кадра |
| `gpu::device` | Копии разделяют владение устройством | Ресурсы с этим handle удерживают его; перегрузки с сырым `SDL_GPUDevice*` заимствуют его |
| `raw()` | Возвращает невладеющий SDL handle | Не освобождайте его вручную и не используйте после уничтожения владельца |

Разместите ресурсы снаружи цикла, а короткоживущий frame scope — внутри. Например, для миникарты сначала завершите кадр текстуры, затем рисуйте её в окно:

```cpp
// Создать до цикла. window уже существует.
auto minimap = window.create_texture({256, 256});
auto minimap_image = mngl::sprite::borrowed(minimap, {0.05f, 0.05f, 0.3f, 0.3f});

// Внутри игрового цикла, после обновления логики:
{
	auto pass = minimap.frame(mngl::color{0.1f, 0.1f, 0.1f, 1.0f});
	pass.draw(mngl::two_d::rectangle_shape{
	    {0.2f, 0.2f, 0.2f, 0.2f}, mngl::color{1.0f, 0.8f, 0.1f, 1.0f}});
	pass.display();
}
auto output = window.frame();
output.draw(minimap_image);
output.display();
```

Если выйти из области frame scope без `display()`, кадр отменяется. Это полезно при исключении: незавершённая работа не отправляется из деструктора. Похожее правило действует у низкоуровневого `gpu::command_buffer`: завершите проходы и явно вызовите `submit()`.

## Ошибки и значения результата

Обычные операции возвращают результат напрямую и бросают исключение при ошибке. Это позволяет обработать неудачную загрузку ресурса в одном `catch` вокруг запуска приложения. Ошибки аргументов обычно имеют тип `std::invalid_argument`, нарушения состояния — `std::logic_error`, ошибки SDL — `mngl::sdl_error`, ошибки аудио — `audio::audio_error`.

У ряда операций есть явные варианты `try_`, возвращающие `std::expected`. Они удобны, когда отсутствие возможности — нормальная ветка логики. Выделение памяти всё ещё может бросить исключение.

```cpp
#include <MNGL/paths.hpp>
#include <iostream>

auto directory = mngl::paths::try_user_data_directory();
if (directory)
{
	std::cout << "Settings directory: " << *directory << '\n';
}
else
{
	std::cerr << directory.error().what() << '\n';
}
```

Не смешивайте эти контракты: `paths::user_data_directory()` уже возвращает `path`; у него не нужно проверять `.has_value()`. Вариант с `std::expected` называется `paths::try_user_data_directory()`.

## Пути к ресурсам и сохранениям

Относительный путь `assets/player.png` вычисляется от рабочего каталога процесса. В IDE он часто отличается от каталога `.exe`. `paths::application_directory()` возвращает каталог ресурсов приложения, а `paths::user_data_directory()` — отдельный персональный каталог для изменяемых данных.

```cpp
#include <MNGL/paths.hpp>

const auto image_path = mngl::paths::application_directory() / "assets" / "player.png";
const auto profile_path = mngl::paths::user_data_directory() / "controls.mnglprofile";
```

Настройте стабильные `APP_ORGANIZATION` и `APP_STORAGE_NAME` до подключения заголовков во всех единицах трансляции. Переименование каталога между версиями может выглядеть как потеря сохранений. [Runtime и пути](../core/runtime-and-utilities.md) показывают конфигурацию и обе модели обработки ошибок.

## Потоки и следующий шаг

Окна, обработку событий и запросы списка устройств выполняйте в главном потоке. Для фонового чтения файлов используйте [async I/O](../core/async-io.md). Для записи 2D-команд из нескольких потоков предназначены отдельные recording contexts с явными `finish()` и `merge()`; см. [параллельную запись](../2d/parallel-recording.md).

Затем выберите одну задачу: [управление игроком](../core/input-recipes.md), [анимация спрайта](../2d/sprite-animation.md), [текст](../2d/text-rendering.md) или [сохранение данных](../core/storage.md). Если пример не запускается, начните с [разбора ошибок](troubleshooting.md).
