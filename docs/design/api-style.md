# Принципы и стиль API MNGL

MNGL делает обычные задачи прямыми и короткими. Разумные настройки по умолчанию
дают готовый результат; явные ресурсы, конфигурации и доступ к SDL/GPU позволяют
расширять поведение по необходимости. Библиотека не навязывает архитектуру приложения.

## Простота и расширяемость

- У обычной операции есть короткий путь без обязательных builders, registries и наследования.
- Детальная настройка доступна через options-структуры, отдельные перегрузки или GPU API.
- Глобальные оптимизации 2D доступны отдельными `enable_*()` / `disable_*()` в
  `mngl::gpu`; основные настройки не требуют изменения обычного цикла отрисовки.
- Модули можно подключать отдельно или через необязательный umbrella `mngl.hpp`.
  Общая инициализация находится в `runtime.hpp`,
  ошибки — в `error.hpp`; `utilities.hpp` остаётся совместимым сборным заголовком.
- Публичные модули включают только необходимые заголовки; они не подтягивают
  `utilities.hpp` ради транзитивных имён и legacy-макросов. Image-модуль подключает
  SDL_image явно там, где он нужен.
  Приложению, которое использует старые глобальные имена, нужно явно подключить
  `utilities.hpp`; для логгера используйте namespaced `logger.hpp`, а не legacy `logger.h`.
- Прикладные и предметные расширения находятся в `extras/` и подключаются явно.
- Публичные фасады в корне `MNGL/` сохраняют короткие include-пути. Их реализация может
  раскладываться по `MNGL/detail/`; внутренние заголовки и `.inc` не являются стабильным API.
- Перемещение реализации не меняет публичные контракты владения, потоков, доставки событий
  и срока жизни ссылок. Документируйте эти контракты у публичного модуля до реорганизации.
- Владеющий ресурсом объект использует RAII. Он перемещается, если это допускает
  backend; копирование разрешено для значений и явно документированных shared handles.
- `raw()` возвращает невладеющий SDL handle. Он не передаёт владение вызывающему.
  Связанный GPU device доступен через `device_raw()`.
- GPU-ресурс, созданный через `gpu::device`, удерживает общее состояние устройства до
  своего освобождения. Перегрузки с сырым `SDL_GPUDevice*` остаются заимствующими; вызывающий
  отвечает за то, чтобы устройство пережило все созданные через них обёртки.
- `gpu::command_buffer` отправляет команды только после явного `submit()`. Если он уничтожен
  активным, деструктор отменяет команды; он не запускает скрытую работу на GPU.

## Имена и интерфейсы

- Новые пространства имён, типы, функции, поля, concepts и enum values используют `snake_case`.
- Короткий getter называется по свойству: `size()`, `position()`, `ready()`.
  Для setter допустимы перегрузка свойства (`window.title(value)`) и `set_` при
  сложной настройке или builder API. Не добавлять `get_` к новым getters без необходимости.
- Действия называются глаголами: `launch`, `read_file`, `submit`, `disconnect`.
- `valid()`/явный `operator bool` означают наличие handle; `ready()` — готовность операции.
- Старые публичные имена могут оставаться aliases для миграции; документация использует новые.
- Нельзя добавлять глобальные служебные символы и имена с двойным подчёркиванием.
  Внутренняя реализация находится в `mngl::detail` или `detail` своего модуля.
- Макросы имеют префикс `MNGL_`; предпочитать типизированный C++ API, когда он подходит.

## Ошибки и асинхронные операции

- Обычные синхронные операции возвращают результат напрямую и бросают исключение при ошибке.
  SDL failures используют `mngl::sdl_error`, ошибки аргументов — `std::invalid_argument`,
  нарушения состояния — `std::logic_error`. Исключение должно хранить исходную ошибку сразу.
- Явные `try_` операции возвращают `std::expected<T, error_type>` и позволяют обработать
  штатный отказ без исключения. Выделение памяти и ошибки пользовательских callbacks
  могут бросать исключения; наличие `expected` само по себе не обещает `noexcept`.
- После запуска асинхронной операции её backend failures попадают в типизированный
  результат. У request есть `ready()` и `result()` для снимка состояния. Получение
  единственного владеющего буфера явно называется `take_data()`.
- Для обычного async I/O `queue.wait(request)` объединяет ожидание, статус, метаданные
  и read buffer в `std::expected`; `poll()` и snapshot остаются для неблокирующих циклов.
- Деструкторы не бросают. Ошибки завершения, которые важны вызывающему, доступны через
  явный `close()`/`submit()`/`wait()` до разрушения объекта.
- Нельзя выпускать C++ исключения через C callbacks SDL или entrypoints модулей.

## C++23 и оформление

- Использовать `std::expected`, `std::span`, `std::string_view`, concepts и стандартные
  RAII-типы по назначению. Не добавлять абстракцию только ради нового синтаксиса.
- Отмечать `[[nodiscard]]` результаты, потеря которых обычно является ошибкой.
  Указывать `noexcept`, когда операция действительно не бросает.
- Использовать явные C++ casts, инициализировать поля и объявлять прямые include dependencies.
- Собственные C++ исходники форматируются `.clang-format`: табы, шаг 4, Allman, предел 110.
  Сторонний код не переформатируется.
- Комментарии объясняют контракт, владение, потоки или причину решения. Текст должен быть
  нейтральным. В руководствах используется русский; существующие точные английские
  контрактные комментарии не требуют перевода при каждом изменении.

## Изменение публичного API

Примеры и module map обновляются вместе с кодом. Механические переименования по возможности
оставляют aliases/wrappers. Изменения полей и моделей ошибок описываются в
[руководстве по миграции](migration.md), поскольку alias не сохраняет такие контракты.

## Форматирование

Конфигурация проверена с LLVM clang-format 23.1.3. Форматирование и проверка собственного кода:

```powershell
./scripts/format.ps1
./scripts/format.ps1 -Check
```

На Linux/macOS: `sh scripts/format.sh` и `sh scripts/format.sh --check`. Эти команды
не включают сторонние заголовки. `BUILD_TESTING=ON` дополнительно компилирует каждый
публичный заголовок отдельно, проверяет совместимые имена и выполняет CTest сценарии.
