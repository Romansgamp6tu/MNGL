# API алгоритмов деревьев

Публичный контракт находится в `MNGL/tree_algorithm_api.hpp` и доступен как `mngl::mods::tree::algorithm`. Он описывает реализацию дерева отдельно от окна, файлового проводника и рендерера. Host передаёт алгоритму модель дерева, а отображение и состояние рабочей области остаются его ответственностью.

## Идентификаторы

Каждый тип дерева получает постоянный строковый ID. Встроенные ID объявлены в `mngl::mods::tree::ids`:

| Тип | ID |
| --- | --- |
| BST | `mngl.tree.bst` |
| AVL | `mngl.tree.avl` |
| Красно-чёрное дерево | `mngl.tree.red-black` |
| Splay | `mngl.tree.splay` |
| Treap | `mngl.tree.treap` |
| B+ tree | `mngl.tree.b-plus` |
| Битовый бор Patricia | `mngl.tree.bitwise-trie` |

ID не зависит от позиции типа в меню или порядка загрузки модов. `algorithm::info()` возвращает ID, отображаемое имя, имя файла, префикс сериализации, поддерживаемые типы ключей и операции, а также возможности анимации.

## Модель и операции

Типы `key`, `node` и `tree` задают общее представление, которое host умеет отображать. `tree` поддерживает бинарные и многопутевые узлы, несколько ключей в узле, метки узлов и связи листьев B+ tree.

Реализация `algorithm` предоставляет следующие действия:

- `create_empty` создаёт пустое дерево;
- `deserialize` читает документ и возвращает его стабильный ID, модель дерева и обнаруженный тип ключей;
- `validate` проверяет структуру и инварианты конкретного алгоритма;
- `find`, `insert`, `insert_many`, `erase`, `merge` и `split` выполняют доступные операции;
- `serialize` записывает дерево в его файловый формат.

`algorithm_info::supported_operations` перечисляет доступные команды: поиск, одиночная и массовая вставка, удаление, слияние и разделение. Host должен сверять наличие команды с этой маской до её показа или выполнения.

## Анимация

`algorithm_info::animations` отдельно перечисляет операции, для которых доступны плавные переходы раскладки, и операции, которые могут вернуть последовательность пошаговых `visual_event`. Например, Splay сообщает пошаговые события вставки; для других операций host может плавно перестроить раскладку после изменения модели. Если `operation_result::animation_events_complete` равен `false`, host может использовать переход раскладки вместо неполной последовательности событий.

## Регистрация реализации

Базовый класс наследуется от `mngl::mods::modable` и имеет общий class ID `mngl::mods::tree::algorithm_class_id`. Для реализации дерева мод регистрирует фабрику через `mod_context::add_implementation`; ID реализации должен совпадать с `algorithm_info::id`:

```cpp
return context.add_implementation<mngl::mods::tree::algorithm>(
    mngl::mods::tree::algorithm_class_id,
    "example.tree.my-algorithm",
    [] { return std::make_unique<my_tree_algorithm>(); });
```

Каждый экземпляр должен возвращать неизменяемую `algorithm_info`, время жизни которого покрывает время работы экземпляра. При запуске приложение загружает пакеты из непосредственных подпапок `mods` рядом с executable. Встроенный BST всегда доступен; типы из модов появляются в выборе дерева только после успешной регистрации фабрики и проверки метаданных. Сейчас приложение проверяет совпадение ID фабрики и `algorithm_info::id`, непустые `display_name` и `serialization_prefix`, поддержку хотя бы одного типа ключа и безопасный `file_stem` из латинских букв, цифр, `_` или `-`. Префиксы сериализации должны быть уникальны.

Реестр `class_registry<algorithm>::implementations()` также возвращает ID владельца и флаг `builtin`. Приложение создаёт экземпляры зарегистрированных фабрик при построении каталога и держит их живыми до уничтожения загрузчика, поэтому код модов не выгружается раньше объектов алгоритмов. Чтобы мод появился в приложении, положите его пакет в подпапку `mods` рядом с исполняемым файлом и перезапустите приложение.

Нативные модули собираются с ABI host-приложения; загрузчик проверяет `binary_abi`. Изменение виртуального контракта требует обновления major-версии API модов.

## Инспекторы инвариантов

Контракт `mngl::mods::tree::invariant_inspector` объявлен в `MNGL/tree_invariant_api.hpp`. Он отделён от алгоритма, поэтому правила структуры остаются в реализации самого дерева, а host показывает только готовые проверки и описание выбранного узла. BST получает встроенный инспектор. Остальные алгоритмы могут регистрировать собственный инспектор как реализацию класса `mngl.tree.invariant-inspector` под тем же implementation ID, что и алгоритм; отдельный мод может расширить дерево без изменений host.

`inspect(tree, key_kind)` возвращает общие проверки с результатом и пояснением. Host запускает эту проверку после открытия или изменения дерева и кэширует отчёт до следующего изменения. `describe_node(tree, key_kind, node_index)` вызывается только для выбранного или наведённого узла, поэтому панель не строит миллион строк деталей заранее. Встроенный BST показывает порядок ключей и дочерние узлы; текущие инспекторы модов показывают:

- AVL — сохранённую высоту узла, высоты детей и баланс; проверку порядка, высот и диапазона баланса;
- красно-чёрное дерево — цвет и чёрную высоту поддерева выбранной вершины; чёрный корень, отсутствие красных соседей и единую чёрную высоту путей;
- Treap — приоритет узла и приоритеты его детей; BST-порядок и min-heap свойство;
- Splay — ключ и дочерние узлы; BST-порядок, связность и структуру корня;
- B+ tree — заполнение выбранного листа ключами или внутреннего узла детьми, пределы заполнения, уровни листьев, разделители и цепочку листьев;
- Patricia — номер критического бита выбранной внутренней вершины, сжатие ветвления, уникальность листьев и связность.

Вкладка «Инварианты и ход» показывает эти проверки, метрики выбранного узла и ход доступной анимации либо путь последнего поиска. Мод может добавлять правила для собственного типа дерева, реализовав этот интерфейс и зарегистрировав фабрику в `mod_context`.

## Сквозной пример: Treap

BST остаётся встроенным алгоритмом. Treap собран отдельной динамической библиотекой в `examples/mods/treap_tree_mod.cpp`; приложение автоматически помещает библиотеку и manifest в `mods/mngl.tree-practicum.treap` рядом с executable. При старте загрузчик регистрирует мод, после чего Treap появляется в выборе типа дерева.

Сборка MSVC генерирует manifest с ABI-тегом текущей сборки. Для обычной конфигурации CMake достаточно собрать приложение и запустить интеграционную проверку:

```powershell
cmake -S . -B build -DMNGL_BUILD_TREAP_TREE_MOD=ON -DBUILD_TESTING=ON
cmake --build build --config Debug --target mngl_demo
ctest --test-dir build -C Debug -R mngl_treap_tree_mod_integration --output-on-failure
```

Интеграционная проверка загружает собранный пакет из файловой системы, создаёт Treap, проверяет вставку, поиск, удаление, массовую вставку, разделение и слияние, затем сохраняет и повторно открывает документ через файловый формат практикума. В окне приложения доступны те же действия и визуализация по общей модели узлов. После сборки перезапустите приложение, чтобы загрузить новый пакет.

## Сквозной пример: Splay

Splay также собран отдельным модом в `examples/mods/splay_tree_mod.cpp`. Он использует тот же ID `mngl.tree.splay` и формат `.tree` (`splay{...}`), поддерживает ключи `int64_t` и конечные `double`, а вставка передаёт холсту последовательность событий поворотов для пошаговой анимации. Остальные операции используют переход раскладки.

AVL собирается как отдельный мод из `examples/mods/avl_tree_mod.cpp` и автоматически попадает в пакет `mods/mngl.tree-practicum.avl` при сборке приложения. Он регистрирует ID `mngl.tree.avl`, сохраняет прежний формат `.tree` (`avl{...}`) вместе с высотой каждого узла, проверяет BST-порядок, баланс и сохранённые высоты, а вставку, удаление, объединение и разделение выполняет через библиотечную реализацию `avl<T>`. Для этих операций приложение показывает переход раскладки; пошаговые события поворотов AVL пока не предоставляет.

Красно-чёрное дерево собирается отдельным модом из `examples/mods/red_black_tree_mod.cpp` и попадает в пакет `mods/mngl.tree-practicum.red-black`. Он сохраняет формат `.tree` с кодом цвета в каждом узле (`0` — красный, `1` — чёрный), проверяет BST-порядок, чёрную высоту, цвет корня и запрет красных родительских пар. Все операции выполняются библиотечным `rb_tree<T>`; приложение анимирует изменения переходом раскладки.

## Сквозной пример: B+ tree

B+ tree вынесено в отдельный мод `examples/mods/b_plus_tree_mod.cpp` и автоматически упаковывается в `mods/mngl.tree-practicum.b-plus`. Он сохраняет ID `mngl.tree.b-plus` и формат `.tree` с fanout, внутренними узлами-разделителями (`I{...}[...]`), листьями (`L{...}`) и их связями. Мод проверяет заполнение узлов, порядок ключей, равную глубину листьев, разделители и цепочку листьев; операции выполняются библиотечным `b_plus_tree<T>`. Слияние и разделение перестраивают дерево с сохранением fanout текущей записи.

Для отдельной сборки B+ модуля используйте опцию `MNGL_BUILD_B_PLUS_TREE_MOD`; сборка `mngl_demo` создаёт пакет мода рядом с исполняемым файлом. После сборки перезапустите приложение, чтобы загрузчик включил его в список доступных типов деревьев.

## Битовый бор как мод

Patricia-битовый бор собирается как независимый мод из `examples/mods/bitwise_trie_mod.cpp`. Он принимает только `int64_t`, поддерживает поиск, вставку, массовую вставку и удаление, а сериализация имеет вид `bitwise_trie{...}`. Для сохранения числового порядка знаковый бит преобразуется перед разбором битов; в модели холста внутренние вершины подписаны номером критического бита, а листья содержат ключи.

Цель `mngl_bitwise_trie_mod_package` кладёт DLL, `mod.json` и `commands.json` в `mods/mngl.tree-practicum.bitwise-trie`. Каталог команд описывает операции мода и загружается только после регистрации алгоритма.

## JSON-каталог команд

Описания операций хранятся в JSON отдельно от реализации. Общий файл приложения — `data/tree_commands.json` рядом с executable. Каталог самого мода — `commands.json` рядом с его `mod.json`; так автор мода может добавить подписи и объяснения команд, не редактируя host. Записи из пакетов не загружаются, пока алгоритм с указанным ID не зарегистрирован.

Формат имеет версию схемы `1`. Для стандартных операций `name` — одно из имён `find`, `insert`, `insert_random`, `erase`, `merge` или `split`. Мод также может объявить собственную команду: для неё каталог задаёт `parameters`, а DLL регистрирует `custom_command_handler` под тем же implementation ID, что и алгоритм дерева.

```json
{
  "schema_version": 1,
  "commands": [
    {
      "algorithm_id": "mngl.tree.bitwise-trie",
      "name": "find",
      "signature": "find(key: int64_t) [F]",
      "description": "Ищет ключ по битам и подсвечивает пройденные ветви."
    },
    {
      "algorithm_id": "mngl.tree.bitwise-trie",
      "name": "prefix_search",
      "signature": "prefix_search(prefix: bit_string)",
      "description": "Находит ключи по старшим битам и подсвечивает совпадения.",
      "parameters": [
        {
          "name": "prefix",
          "label": "Битовый префикс",
          "type": "bit_string",
          "hint": "1–64 бита, например 10"
        }
      ]
    }
  ]
}
```

Стандартная запись показывается только если алгоритм объявляет операцию в `supported_operations`. Собственная команда показывается, только если зарегистрированный обработчик отвечает `true` на `supports_command(name)`. Каждый параметр имеет уникальные `name`, отображаемый `label` и тип: `text`, `bit_string`, `int64`, `double` или `boolean`; `hint` необязателен. Host строит форму из JSON, преобразует значения в типизированные `command_argument`, передаёт их обработчику и применяет возвращённое сообщение, подсветку узлов и признак изменения дерева.

Базовый контракт расположен в `MNGL/tree_custom_command_api.hpp`. Обработчик наследуется от `mngl::mods::tree::custom_command_handler` и регистрируется отдельной фабрикой через `mod_context::add_implementation`. Для `command_result::highlighted_nodes` используйте индексы узлов переданной модели. Если `changed` равен `true`, host проверяет дерево и записывает новую сериализацию. Этот интерфейс добавляет новый class ID и не меняет vtable существующего `algorithm`.

В моде Patricia-бора `prefix_search` принимает строку из `0` и `1` длиной от 1 до 64 бит. Битовый префикс задаётся для преобразованного представления `int64_t`, поэтому старший бит `0` соответствует отрицательным значениям, а `1` — неотрицательным. Команда возвращает число совпавших ключей и подсвечивает путь поиска вместе с совпавшими листьями.

Описания из пакета мода заменяют запись общей справки с тем же ID дерева и именем команды; дубликаты между пакетами пропускаются с диагностикой. Общий файл хранит описания стандартных операций, а пакет может добавлять собственные команды или уточнять описание заменённой реализации.

После сборки `mngl_demo` пакет появится в `mods/mngl.tree-practicum.splay`. Запустить проверку всего пути для Splay можно так:

```powershell
cmake --build build --config Debug --target mngl_demo
ctest --test-dir build -C Debug -R mngl_splay_tree_mod_integration --output-on-failure
```

Проверка загружает DLL из пакета, создаёт дерево, проигрывает события вставки и проверяет, что они дают ту же модель, что и алгоритм. Она также проверяет поиск с переносом найденного узла в корень, массовую вставку, удаление, split/merge и сохранение с повторным открытием файла.
