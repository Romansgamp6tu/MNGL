# Контракт модов MNGL v1

Статус: API и загрузчик v1 реализованы в `MNGL/mods.hpp` и `MNGL/mod_loader.hpp`; host и отдельный пример мода находятся в `examples/mods/`.

## Цель и границы

`mngl::mods` даёт приложению управляемые точки расширения. Разработчик приложения объявляет, какие функции, свойства и фабрики классов можно менять. Мод может заменить объявленную функцию, обернуть её, изменить объявленное свойство или зарегистрировать реализацию класса.

Механизм не патчит произвольный машинный код и не даёт доступ к любому полю класса. В C++ расширяемость должна быть объявлена явно: каждый вызов функции идёт через слот, а каждое изменяемое свойство имеет зарегистрированные getter, setter, тип и правила проверки.

В первой версии моды — доверенные нативные библиотеки, загружаемые приложением. Мод не обязан менять или пересобирать базовую библиотеку MNGL. Бинарный мод собирается под платформу, архитектуру и C++ runtime целевого приложения; совместимость между произвольными компиляторами не обещается.

## Идентификаторы

Идентификаторы модов и точек расширения постоянны и не зависят от имён C++ типов или файлов.

- `mod_id` уникален, состоит из ASCII букв в нижнем регистре, цифр, точек и дефисов. Пример: `example.fast-tree`.
- `extension_id` и `class_id` задаются владельцем в собственном пространстве имён. Примеры: `mngl.demo.tree.insert`, `mngl.demo.tree.node-gap`.
- Переименование C++ класса не меняет его `class_id`. Пример: `mngl.demo.tree`.
- Повторная регистрация одного ID считается конфликтом и диагностируется при загрузке. Реестр не выбирает победителя по случайному порядку загрузки. Идентификаторы должны соответствовать шаблону `[a-z0-9][a-z0-9._-]*`.

Макросы регистрации обязаны принимать явные ID. Автоматически выводить их из `typeid`, имени класса или адреса функции нельзя: такие значения нестабильны между сборками.

## Версии и manifest

Версия мода использует `MAJOR.MINOR.PATCH`. Версия API модов MNGL использует `MAJOR.MINOR`:

- изменение `MAJOR` означает несовместимое изменение интерфейса;
- увеличение `MINOR` добавляет совместимые возможности;
- загрузчик принимает мод, если major совпадает, а minor-версия host не ниже требуемой модом.

Пакет мода содержит manifest и бинарный файл для текущей платформы. Минимальный manifest:

```json
{
  "schema_version": 1,
  "id": "example.fast-tree",
  "name": "Fast Tree",
  "version": "1.0.0",
  "api_version": "1.0",
  "binary_abi": "<точное значение native_binary_abi_tag()>",
  "binary": "bin/fast_tree.dll",
  "dependencies": {
    "example.base": ">=1.2.0 <2.0.0"
  }
}
```

`dependencies` — необязательный объект, где ключом служит `mod_id`, а значением — диапазон версии требуемого мода. Поддерживаются `*` или один либо несколько разделённых пробелами условий `=`, `<`, `<=`, `>` и `>=` для версий `MAJOR.MINOR.PATCH`; несколько условий объединяются через AND. Например, `">=1.2.0 <2.0.0"` принимает версии от 1.2.0 включительно до 2.0.0 исключительно. Диапазоны-каретки, тильды и запятые пока не поддерживаются.

`binary_abi` — точный тег ABI, который сравнивается с тегом host. В `mod_loader_options` по умолчанию используется `native_binary_abi_tag()`; приложение может передать собственный тег, если ему нужно зафиксировать дополнительные параметры сборки. Путь `binary` относительный к каталогу мода, не может содержать `.` или `..` и после разрешения symlink должен оставаться внутри пакета. Manifest — UTF-8 JSON размером не более 1 MiB; неизвестные поля отклоняются.

Загрузчик ищет manifest с именем `mod.json`. `mod_loader::load_package(path)` загружает один пакет, если его зависимости уже загружены и версии подходят. `load_all(path)` читает непосредственные подпапки каталога модов и загружает пакеты в топологическом порядке: сначала зависимости, затем использующие их моды; независимые пакеты обрабатываются в стабильном порядке по ID. Для отсутствующей зависимости, несовместимой версии и циклической зависимости возвращается ошибка с нужными ID и версиями. При цикле сообщение показывает путь, например `a -> b -> a`; отдельные циклы показываются независимо, а модули, зависящие от нескольких циклов, ссылаются на каждый из них. Зависимые от цикла модули отклоняются с отдельным объяснением. Ошибка пакета не мешает загрузить независимые пакеты.

Библиотека должна экспортировать C-символ `mngl_mod_load_v1`. Необязательный `mngl_mod_unload_v1` вызывается при отключении мода после завершения его активных вызовов и уничтожения созданных им экземпляров:

```cpp
#include <mngl/mod_loader.hpp>

extern "C" MNGL_MOD_EXPORT bool MNGL_MOD_CALL mngl_mod_load_v1(mngl::mods::mod_context& context)
{
	context.replace_function<bool(tree_base&, key_type)>("mngl.demo.tree.insert", &fast_insert);
	return true;
}

extern "C" MNGL_MOD_EXPORT void MNGL_MOD_CALL mngl_mod_unload_v1()
{
	// Остановить и присоединить потоки, созданные модом.
}
```

`load_v1` возвращает `true`, если инициализация завершилась. При `false` или исключении загрузчик удаляет все регистрации мода и вызывает `unload_v1`, если он экспортирован. Исключения не должны пересекать ABI-границу; загрузчик ловит их как дополнительную защиту.

## Функции

Расширяемая функция объявляется как типизированный слот с постоянным `extension_id` и реализацией по умолчанию. Код приложения вызывает слот; прямой вызов реализации в обход слота не заменяется.

Поддерживаются два действия:

- `replace` подменяет реализацию целиком. На один слот допускается одна активная замена. Несколько замен приводят к диагностике конфликта и отключению конкурирующих регистраций для этого слота.
- `around` оборачивает следующую реализацию и может вызвать `next` не более одного раза. Один мод может зарегистрировать не более одной замены и одной обёртки на слот. Обёртки вызываются от большего `priority` к меньшему, затем по `mod_id` в лексикографическом порядке; порядок одинаков при каждом запуске. Приоритет по умолчанию — `0`.

Если для слота зарегистрировано несколько `replace` с одинаково допустимым API, все конфликтующие замены отклоняются, и вызывается реализация приложения по умолчанию. `around`-обёртки при этом продолжают работать поверх выбранной реализации. Сигнатура функции фиксируется точкой расширения; несовместимая регистрация отклоняется. Исключения не должны пересекать границу вызова: исключение из `replace` отключает эту регистрацию и передаёт текущий вызов реализации по умолчанию. Исключение из `around` отключает обёртку: если она ещё не вызвала `next`, host продолжает со следующим слоем; если вызвала — использует сохранённый результат `next` и не вызывает его повторно. Ошибка записывается в диагностику с ID мода и слота.

## Свойства и переменные

Изменяемое поле объявляется как свойство с `extension_id`, типом, областью действия, значением по умолчанию, getter, setter и необязательной проверкой.

В v1 поддерживаются типы `bool`, целые числа фиксированной ширины, `float`, `double`, строки UTF-8 и перечисления со стабильными строковыми значениями. Сырые указатели, ссылки и произвольные C++ объекты через общий API не передаются. Автоматическое сохранение настроек в v1 поддерживает `bool`, фиксированные целые типы, `float`, `double` и `std::string`; `instance`-свойства и пользовательские типы не сохраняются.

Области действия:

- `global` — одно значение на приложение;
- `class_default` — значение по умолчанию для новых экземпляров класса;
- `instance` — значение конкретного объекта, адресуемого непрозрачным handle, выданным host. Handle действует, пока объект жив, и не сохраняется между запусками.

Мод может задавать и менять своё значение-override через API свойства. При чтении реестр возвращает выбранный override, а если его нет — значение host getter или значение по умолчанию. Override проверяется валидатором; host-код должен читать свойство через слот, чтобы увидеть значение мода. Host-запись через setter обновляет базовое значение приложения и может быть отклонена setter-ом. Область `instance` задаёт объект по host handle, а `class_default` влияет только на новые экземпляры. Мод не получает смещение поля в памяти и не может безопасно менять его простым `reinterpret_cast`.

Приоритет override по умолчанию — `0`; побеждает большее значение `priority`, а при равенстве — меньший `mod_id` в лексикографическом порядке. Победившее значение и его источник отображаются в диагностике. Штатное значение приложения сохраняется как fallback при отключении мода.

### Настройки между запусками

Host загружает сохранённые значения после `load_package()` или `load_all()`, когда моды уже объявили свои overrides. `registry.settings()` возвращает доступные для интерфейса настройки с ID, типом и текущим значением. `registry.set_setting(mod_id, property_id, text, &error)` меняет значение; тип разбирается строго, а валидатор свойства применяется повторно. Host вызывает `save_settings(path)` перед выгрузкой модов или завершением работы.

```cpp
for (const auto& issue : mods.load_settings("config/mod-settings.ini"))
	std::cerr << issue.message << '\n';

for (const auto& setting : mods.settings())
	std::cout << setting.mod_id << ' ' << setting.property_id << " = " << setting.value << '\n';

std::string error;
if (!mods.set_setting("example.tree-tools", "demo.tree.node-gap", "36.5", &error))
	std::cerr << error << '\n';
mods.save_settings("config/mod-settings.ini");
```

Файл `MNGL_MOD_SETTINGS` v1 использует таб-разделённые записи `mod_id`, `property_id`, тип, значение; байты, которые нельзя безопасно записать в строку, кодируются как `%HH`. Неизвестные записи сохраняются при следующем сохранении, поэтому настройки временно отсутствующего мода не пропадают. Несовпадающий тип или отклонённое валидатором значение сообщается в diagnostics и не применяется. Настройки остаются отдельной от manifest функцией host-а: приложение само выбирает путь хранения и интерфейс редактирования.

## Классы

Расширяемый базовый класс регистрируется под постоянным `class_id`. Мод может добавить новую реализацию с новым ID или заменить фабрику существующей реализации.

Фабрика возвращает объект базового интерфейса. Регистрация проверяется на совместимость базового типа и фабрики. Для одного ID реализации допускается одна активная фабрика-замена; конкурирующие регистрации отклоняются, и остаётся исходная фабрика. Замена влияет на новые экземпляры; существующие объекты не пересоздаются автоматически.

Для замены конкретной реализации указывается её ID, например `mngl.demo.tree.bst`. Замена базового интерфейса целиком запрещена: другие реализации этого интерфейса должны оставаться доступными.

## Жизненный цикл и ошибки

Мод регистрирует функции, свойства и классы во время явной точки входа. Реестр хранит владельца каждой регистрации. Если инициализация мода завершается ошибкой, все его регистрации откатываются.

При отключении мода его функции, свойства и фабрики удаляются; слоты и свойства возвращаются к следующему допустимому обработчику, значению или реализации приложения. Загрузчик закрывает вход новым вызовам, снимает регистрации и откладывает `unload_v1`, пока не закончатся активные callbacks и не будут уничтожены объекты, созданные фабриками мода. Callback-копии, которые уже находятся в выполняющемся вызове, и каждый фабричный объект удерживают библиотеку загруженной. `mod_loader::unload(id)` возвращает `deferred`, если такой код или объект ещё используется. Мод-провайдер нельзя выгрузить, пока загружен, загружается или ожидает отложенной выгрузки зависящий от него мод; в этом случае `unload` возвращает `dependency_in_use` и называет зависимый мод. `unload_all()` выгружает зависимые моды раньше провайдеров. Если зависимая выгрузка отложилась из-за живого объекта, вызовите `collect_deferred()` после уничтожения объекта, а затем повторите `unload_all()` для провайдера. После окончания вызовов и уничтожения объектов host вызывает `collect_deferred()` в синхронизированной точке приложения, когда callbacks и деструкторы уже вернулись; он завершает callback отключения и закрывает DLL/so из стека host. `load_package`, `unload` и `unload_all` также собирают уже готовые отложенные выгрузки. Держите `mod_loader` живым, пока существуют созданные модами объекты, и не запускайте сборку выгрузок параллельно с вызовами или уничтожением объектов. Мод должен останавливать собственные фоновые потоки в `unload_v1`.

Ошибки manifest, несовпадение версии API, неизвестные ID, конфликты и ошибки инициализации должны содержать `mod_id` и конкретный `extension_id`, если он известен. Ошибка одного мода не должна останавливать загрузку остальных.

## Декларативные макросы и реестр

В `MNGL/mods.hpp` есть декларативные макросы для host. Их вызывают на уровне namespace в `.cpp` файлах после объявления типов; при старте host применяет собранные декларации к своему реестру. Идентификаторы передаются явно строковыми литералами. Дубли одинаковой декларации из нескольких translation unit сворачиваются; конфликтующие декларации с одним ID целиком пропускаются и попадают в диагностику.

```cpp
struct tree_base : mngl::mods::modable
{
	virtual bool insert_impl(key_type key) = 0;
	virtual ~tree_base() = default;
};

REGISTER_MODDABLE_CLASS(tree_base, "mngl.demo.tree");
REGISTER_MODDABLE_FUNCTION(tree_base, "mngl.demo.tree.insert", &tree_base::insert_impl);
REGISTER_MODDABLE_VALUE_PROPERTY(tree_base, float, "mngl.demo.tree.node-gap",
                                 mngl::mods::property_scope::global, 24.0f);
REGISTER_MODDABLE_FACTORY(tree_base, "mngl.demo.tree", "mngl.demo.tree.bst", make_bst_tree);
```

`REGISTER_MODDABLE_FUNCTION` выводит сигнатуру из обычного function pointer, member function pointer или лямбды с однозначным `operator()`. Для перегруженной или generic-функции есть вариант `REGISTER_MODDABLE_FUNCTION_AS(Type, Signature, Id, Fallback)`. Свойство с host getter/setter объявляется через `REGISTER_MODDABLE_PROPERTY`; валидатор можно добавить через `REGISTER_MODDABLE_VALIDATED_PROPERTY`.

После объявления всех host-точек расширения приложение один раз применяет декларации. Оно должно вызывать функцию через слот и читать переопределяемое значение через `property_slot::get()`:

```cpp
mngl::mods::registry mods;
mods.apply_declarations();

auto& insert = mods.function<bool(tree_base&, key_type)>("mngl.demo.tree.insert");
auto& node_gap = mods.property<float>("mngl.demo.tree.node-gap");
auto& tree_classes = mods.classes<tree_base>("mngl.demo.tree");

const bool inserted = insert(tree, key);
const float current_gap = node_gap.get();
auto tree_instance = tree_classes.create("mngl.demo.tree.bst");
```

Host передаёт моду контекст с его постоянным ID; мод регистрирует замену, обёртку или override свойства:

```cpp
auto context = mods.for_mod("example.fast-tree");
context.replace_function<insert_signature>("mngl.demo.tree.insert", &fast_insert);
context.around_function<insert_signature>("mngl.demo.tree.insert", 10,
                                          [](auto next, tree_base& tree, key_type key)
                                          { return next(tree, key); });
context.set_property<float>("mngl.demo.tree.node-gap", 32.0f);
context.add_implementation<tree_base>("mngl.demo.tree", "mngl.demo.tree.fast",
                                      [] { return std::make_unique<fast_tree>(); });
context.replace_factory<tree_base>("mngl.demo.tree", "mngl.demo.tree.bst",
                                   [] { return std::make_unique<instrumented_bst>(); });
```

`REGISTER_MODDABLE_*` — макросы host-деклараций, а не регистрации внутри DLL мода. `registry.remove_mod(id)` снимает runtime-регистрации и overrides указанного мода, но самостоятельно не управляет DLL. Для нативной загрузки host подключает `mngl/mod_loader.hpp`, создаёт `mod_loader` после `registry` и вызывает `load_package` или `load_all`. API header-only; host и мод должны использовать совместимый C++ ABI, совпадающий с `binary_abi`.

```cpp
mngl::mods::registry mods;
mods.apply_declarations();

mngl::mods::mod_loader loader(mods);
for (const auto& result : loader.load_all("mods"))
	if (!result)
		std::cerr << result.mod_id << ": " << result.message << '\n';

// Отключение снимает регистрации; живые экземпляры могут отложить бинарную выгрузку.
const auto result = loader.unload("example.fast-tree");
// После уничтожения объектов мода завершите отложенные выгрузки.
loader.collect_deferred();
```

## Этапы реализации

1. Зафиксировать контракт v1 и публичный синтаксис точек расширения.
2. Реализовать типизированные слоты функций, свойства, реестр и детерминированное разрешение конфликтов без загрузчика DLL.
3. Добавить регистрацию фабрик классов, откат регистрации при ошибке и безопасное отключение модов.
4. Реализовать manifest-проверки, загрузку нативной библиотеки с проверкой ABI-тега и отложенное отключение.
5. Собрать демонстрационный host и отдельный пример мода, затем описать создание и отладку мода. Выполнено: цель `mngl_mod_host` загружает `example.tree-tools`, а инструкция находится в `mods/creating-and-debugging.md`.
6. Автоматизировать полный цикл независимой сборки, загрузки, замены функции и свойства, конфликтов, ошибочных manifest/ABI, отложенной выгрузки и возврата штатного поведения. Выполнено: CTest цель `mngl_mod_integration` запускается в CI.
7. Добавить зависимости между модами: проверку диапазонов версий, порядок загрузки, ошибку цикла и выгрузку зависимых модов раньше провайдеров. Выполнено: сценарии покрыты CTest интеграционной проверкой.

## Критерии завершения контракта

Первый этап завершён, когда согласованы:

1. схема manifest, правила ID и версионирование;
2. семантика `replace`, `around` и конфликтов;
3. типы и области действия свойств;
4. добавление класса и замена его фабрики;
5. требования к сборке и бинарной совместимости модов.

Шаги 1–7 реализованы; успешный жизненный цикл, зависимости и основные ошибки загрузки покрыты интеграционной проверкой. Дальнейшие изменения публичного API требуют отдельного обновления контракта и версии API.
